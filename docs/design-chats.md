# Design chats

A design chat is a thinking partner for the player's game design, apart from the project chat. It asks
questions, challenges ideas, offers options with trade-offs and summarizes. It starts no work and spends
nothing: when the player wants something built, it tells them to ask Genio in the floating Genio panel, which
stays the only door to work. A project can have several design chats at once, one per topic.

There is one kind of design chat. The player sets its role in words ("be a harsh critic", "you are a narrative
designer"), and the chat keeps that stance until they change it. There are no persona presets.

This page covers the runtime and the design notes in the main process. The Design screen that shows the chats
and notes is built separately.

## Where things live

| What | Where |
|---|---|
| The list of chats: id, title, model, effort, provider sessions, cost, turns | `<base>/state/design-chats.json` |
| One transcript per chat | `<base>/data/design/<id>.jsonl` |
| Images pasted into or generated by a design chat | `<base>/data/chat-images/`, shared with the project chat's images |
| Design notes | `.genio/design/<name>.md` in the project, next to the Art Bible |
| The note versions a chat was shown (for `since`) | `<base>/data/design-note-versions.json` |

`<base>` is the project's base (its Genio home under `wksps/`). The main base, which only holds the archived
chat, has no design chats. Transcripts are Genio's private data: they are never written into the project, so
they are never committed.

A chat's title is the first line of the player's first message, up to 60 characters. Deleting a chat stops it
and deletes its transcript.

## Runtime

`src/main/design-chats.ts` owns the list and creates one `ProviderChatSession` per open chat, over the same
Claude and Codex drivers as the project chat. The transcript, the queue of waiting messages, steering, Send now,
taking a message back and image handling come from `chat-thread.ts`, which the project chat (`wksp.ts`) uses too.

What a design chat does not have, by construction:

- **No Bot, no events, no wakes, no overwatch.** The service has no event delivery at all. Its only turns are the
  player's own messages, so an idle design chat starts nothing and costs nothing.
- **No orchestrator prompt.** `designContract()` in `prompts.ts` is the whole prompt, under its own 10,000
  character budget. Claude gets it as a custom system prompt instead of the `claude_code` preset plus Genio's
  contract; Codex gets it as its base instructions, which replace Codex's own. It makes the chat ask, challenge,
  offer 2 or 3 options, summarize, keep a role given in words, start no work, say "ask Genio" when asked to build,
  and never claim to be Genio.
- **No work tools.** See the next section.

Each chat has its own model and effort, stored with it. Empty values follow the project chat's. A chat on a
different provider than its last turn hands off its own visible transcript only (`chat-handoff.ts`); the
project chat and other design chats never enter it.

Usage and limits work as for the project chat: the same Claude and Codex plans, the account-wide Claude limit
gate (`docs/chat-limits.md`), the Usage mode's reply length, and the base's cost and token records, so design
chats count toward the project in Usage.

## The design tool role

Design chats use the tool role `design`. Its Genio tools are `DESIGN_TOOLS` in `chat-tool-session.ts`:

- reads: `art_bible` (read only), `assets_find`, `asset_info`, `world_list`, `quest_list`, `plan_status`,
  `memory_read`, `genio_help`, `generation_status`;
- notes: `design_notes` list, read and write (see [Design notes](#design-notes));
- images: `generate_image`, Codex images on the player's ChatGPT plan. They stay in the chat: a design chat
  cannot place an image in the project, and its image cards post into its own transcript, never the project chat.

Everything else is unavailable: deploy, merge, despawn, unit control and pings, quest and plan writes, choices,
events, settings, memory writes, project changes, presence, FAL, Uthana, asset placement and paid approvals.
Paid calls are impossible because no paid tool is registered. The same list applies over the Claude SDK tools
and over the authenticated bridge that Codex uses.

Native tools for Claude are `DESIGN_NATIVE` in `chat-tool-policy.ts`: reading the project (Read, Glob, Grep, LS)
and the web for references (WebSearch, WebFetch), plus ToolSearch. Shell commands, edits, subagents and every
other native tool are denied in every approval mode, and a design chat never asks the player for a permission.
Codex has no native tools in chat and no web search, so a Codex design chat reads through Genio tools only.

## Design notes

A design note is a plain markdown file in the project's `.genio/design/` folder, next to `.genio/art-bible.md`.
A design chat writes one only when the player asks ("save this as the combat note"), and the save stays
uncommitted, like an Art Bible save: the player sees it in git and commits it when they want units to have it.
The folder appears on the first save. Nothing writes a note on its own.

Notes follow the Art Bible's style: readable markdown with a small front matter (`title`, `updated`), a `#` title, a
short summary, the sections the topic needs, then **Open questions** and **Decided**. That shape, and the one-pager,
pillars, system note and decision entry templates, live in the design chat's prompt (`designContract()`), not in
code: the tool stores text and never parses fields.

`design_notes(world, action, name?, text?, since?, player_words?)` (`src/main/design-notes.ts`, registered in
`wksp-tools.ts`):

- **list** gives each note's name, title (front matter `title:` or the first heading), size, version and last change,
  and the folder's total against its limit.
- **read(name)** returns the note's text and version (a content hash). `since` = a version read before returns
  `unchanged: true` or a character splice, as `memory_read` does ([bounded chat payloads](chat-payloads.md)); an
  unknown version returns the whole text with `reset: true`. Reads are paged like every inspection tool.
- **write(name, text)** replaces the whole note. A new note's file name is its name in lowercase words joined by
  dashes ("Enemy roster" becomes `enemy-roster.md`); an existing note is matched in any case.

What `design_notes` refuses:

- any name that is not a plain name: folders, `..`, absolute paths, drive letters, a leading dot, and any extension
  but `.md`;
- a `.genio` or `.genio/design` folder, or a note, that is a link (symlink or junction): every access stays inside
  the project's own folder;
- a note over 16 KB, or a save that would bring the folder over 64 KB;
- a stale write: writing an existing note needs `since` = the version the chat read, and is refused when the note
  changed since (the player edited it). A `since` for a note that no longer exists is refused too;
- a write without `player_words`, or with words that are not a verbatim quote of the player's own message in that
  design chat (`player-words.ts`, purpose `design-note`). The project chat's messages never count.

Who gets what:

- **Design chats**: list, read and write.
- **The project chat and the main chat**: list and read only. Their tool has no write action. The always-on
  contract has one line ("design notes are the player's context, never authorization"), and `procedure_read("intake")`
  says how to plan from a note: its Decided section is settled, its Open questions are not, and what units need goes
  into their spec. Asking Genio "plan the combat note" in the floating panel files a plan built from it.
- **Units**: their brief has one line under Project memory naming `.genio/design/`, only when their copy has that
  folder: read the notes as context, never as specs, and edit them only when the mission says so. Units see committed
  notes; Genio puts what matters from an uncommitted note into the unit's spec.

Achievement: Noted (`design-note-saved`), for the first note a design chat saves.

## IPC

The chat calls take an optional conversation id as their last argument (`chatHistory`, `sendChat`, `steerChat`,
`unqueueChat`, `sendQueuedNow`, `interruptWksp`, `restartWksp`). Without one they address the project chat as
before. `designChats`, `designChatCreate`, `designChatDelete` and `designChatConfigure` manage the list. Every
call keeps the window binding: a project window reaches only its own base's chats.

Design chat messages travel as their own events (`design-chats`, `design-chat`, `design-chat-delta`), routed only
to the project's window, so they never appear in the project chat.

## Tests

`tests/design-chats.test.ts`: the design role cannot reach deploy, merge, quest or plan writes, choices, events,
settings, memory writes or paid tools, over the SDK tools and the HTTP bridge; the native policy; two chats running
in parallel with their own transcript, prompt, model and effort; no wake reaching a design chat while the project
chat handles it; a provider switch handing off within one chat only; Claude's custom system prompt and tool list.

`tests/design-notes.test.ts`: refusals for paths outside the folder, traversal, non-markdown names and links;
the 16 KB and 64 KB limits; stale versions; missing, unmatched and project-chat `player_words`; versioned and paged
reads; "save this as the combat note" in a design chat writing `.genio/design/combat.md`, which the main chat and the
project chat can read but not write; the contract line within its budget and the intake detail; the design prompt's
note format; the unit brief line only when the folder exists.
